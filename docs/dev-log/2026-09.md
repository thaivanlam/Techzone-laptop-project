## 2026-09-12 — Commit and push the session record from the export itself

**Commits:** pending — superproject (`scripts/export_session.py`,
`.claude/settings.json`, `docs/`, `CHANGELOG.md`). No backend or frontend code
changed. The records themselves are committed in `Techzone-session-history`.

**Context.** The exporter written earlier the same day wrote its records and
stopped there; committing and pushing them was a manual step, listed in the
landing checklist. That leaves the one thing the whole mechanism exists for —
outliving the transcript, which the CLI deletes after 30 days — depending on
somebody remembering a second command. The state of the history repository bore
this out: two modified records and one untracked one, from earlier runs, sitting
uncommitted.

**Changes.**

- `scripts/export_session.py` — a new `publish()` runs after the records are
  written. It stages `sessions/` only, commits (`Record session <date> —
  <title>`, or `Record N sessions (<span>)`), and pushes the current branch,
  setting an upstream if it has none. New `--no-commit` and `--no-push`, and the
  environment variables `TECHZONE_SESSION_HISTORY_AUTOCOMMIT` /
  `…_AUTOPUSH`, opt out.
- `.claude/settings.json` — the `SessionEnd` hook timeout goes from 120s to
  300s, since a push now happens inside it.
- `docs/dev-log/sessions.md` — a new "Committing and pushing" section: what the
  exporter does, the opt-outs, and what happens when the push fails.
- `docs/development/developer-guide.md`, `CHANGELOG.md` — checklist item 5 and
  the changelog entry follow.

**Four things it deliberately does not do.**

1. **Stage the whole repository.** Only `sessions/` is added, so a person
   editing the history repository's README does not find it swept into an
   automated commit.
2. **Recover from a rejected push.** A push that fails because the branch moved
   on elsewhere is reported and left alone. Rebasing or merging history nobody
   has looked at, unattended, from a hook, is worse than a record that lands one
   session late.
3. **Fail anything.** Every git call is wrapped; a missing remote, an expired
   credential or an absent git binary prints to stderr and the export still
   returns 0. The hook must never break the session it fires from.
4. **Wait for a credential.** `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`
   are set for every call. A hook has no terminal for a prompt to appear on, so
   a missing credential would otherwise block until the timeout killed it.

There is also a guard against the failure mode the whole design exists to
prevent: an output directory that resolves inside this repository is refused
before anything is written, and `publish()` refuses to commit there as well.

**Verification.** Ran the exporter with `--no-push`, which swept up the three
records left over from earlier runs as `Record 2 sessions (2026-09-12)`; then
without it, which reported "session records already committed" and pushed. The
history repository is level with its remote.

## 2026-09-12 — Record every session, and keep the records out of this repository

**Commits:** pending — superproject (`scripts/`, `docs/`, `CLAUDE.md`,
`CHANGELOG.md`, `.claude/settings.json`). No backend or frontend code changed.
The records themselves are the first commit of a new repository,
`Techzone-session-history`.

**Context.** The question was how to document every session with the AI coding
assistant. The raw material already existed and nobody had looked at it: 24
JSONL transcripts, 38 MB, in the assistant's own store outside the repository.
Two properties made it unusable as it stood — the CLI prunes that store after 30
days and the oldest session was three weeks old, and the bulk of it is tool
output rather than anything a reader wants.

**Changes.**

- `scripts/export_session.py` — new. Reads a transcript and writes one markdown
  record per session: a list of exchanges, each a prompt and the reply that
  closed that turn, plus the session's metadata, files modified and commits
  produced. Redaction runs on everything it emits. `--check` fails when a record
  is missing or stale; `--from-hook` reads the hook payload on stdin.
- `.claude/settings.json` — new. A `SessionEnd` hook runs the exporter, so the
  records do not depend on anyone remembering.
- `docs/dev-log/sessions.md` — new. The pointer to the private repository that
  holds the records, and the procedure for producing them.
- `docs/architecture/decisions/0011-session-records-in-a-private-repository.md`
  — new ADR.
- `CLAUDE.md`, `docs/README.md`, `docs/dev-log/README.md`,
  `docs/development/developer-guide.md`, `CHANGELOG.md`, `.gitignore` — the rule,
  the index rows, the landing checklist.

**How the shape changed three times.** Worth recording, because two of the three
turns were caused by looking at the output rather than by planning.

1. **Prompts only.** The first version kept prompts and dropped replies, on the
   assumption that replies were the bulk of a transcript. Reading the result
   showed the cut was in the wrong place: "chạy docker và load testing cho tôi"
   records the request and loses the result — 11 060 samples, no errors, p95 of
   102 ms on the ordering path, BUG-22 found and BUG-12 re-characterised.
2. **Prompt plus the closing reply.** Measured before changing anything: across
   24 sessions, 80 prompts and 146 KB of assistant prose, of which the *closing*
   reply of each turn is 98 KB, median ~1 300 characters. The rest is narration
   between tool calls — progress, not outcome. Records went from 118 KB to
   232 KB, still 0.6% of the raw store.
3. **Committed somewhere else.** Widening to replies made the privacy question
   concrete. A record is now a conversation quoted whole, and this repository is
   public. Redaction by pattern reduces the risk but cannot bound it, so the
   records moved to a private repository and this one keeps only a pointer.

**Three extraction faults, fixed before the records were trusted.**

1. **Commits attributed to the wrong session.** The first version scanned every
   tool result for git's `[branch 1234567]` output. The session doing this work
   had run a `grep` over the transcripts *for that very pattern*, so its own
   record claimed three commits from a session in August. Fixed by correlating a
   result back to the `tool_use` that produced it and requiring that call to
   have run `git commit` in command position. Every SHA now resolves to a real
   commit in the superproject or one of the submodules.
2. **`jdk-21.0.7.6` masked as a host address.** A four-part version number is
   shaped exactly like a dotted quad. The masker now skips one preceded by a
   version cue, and still masks a bare public address.
3. **Prompt counts read as far too low.** The transcripts carry a `last-prompt`
   record rewritten in place on every turn — 97 copies of one string in the
   longest session, which looked like 97 prompts gone missing. A latch, not a
   log; the six real prompts were all there.

**Two redaction gaps, both found only after replies were captured.**

1. **A truncated Stripe key passed through.** `sk_test_51SXfeX...` carries seven
   characters of key material; the pattern required eight. Threshold lowered to
   four — the rule in [README.md](README.md) forbids a shortened key as firmly
   as a whole one.
2. **A JSON-quoted key never matched at all.** `"MYSQL_PASSWORD": "value"` puts
   a closing quote between the name and the colon, which the `KEY=value` rule
   did not allow for. The more serious of the two: `launch.json` and the Compose
   files are exactly that shape. The rule now accepts an optional quote.

Masked values went from 5 to 16 after both fixes. None of the sixteen is
sensitive — local development passwords and Stripe *test* keys. The finding is
not that something leaked, but that a first redaction list is wrong in ways only
new input reveals. That is also the argument for the private repository: the
masker is a second line, not the guarantee.

**A fourth fault, caused by the rewrite itself.** Rewriting the local commits
left this session's record citing two SHAs that no longer existed. Verifying
them was not enough: `git cat-file` still finds a rewritten commit, because the
object survives until garbage collection. The exporter now tests
**reachability from a ref** — `git rev-list --all` in the superproject and both
submodules — and drops a SHA nothing can reach, while keeping every one that
resolves in any of the three. If git cannot be run at all it drops nothing, on
the grounds that an unverifiable list beats a silently emptied one.

**Notes.** Two limitations are inherent rather than bugs. A session's own final
commit is missing from its record, because the record is generated before that
commit exists — the hook regenerates it at session end, which is why the history
repository usually has one uncommitted change waiting at the start of the next
session. And a commit made with `git commit -q` prints no `[main <sha>]` line,
so the exporter has nothing to attribute; `git log` is the authority either way.

The earlier local commits from this session were rewritten rather than amended,
so the session records never entered this repository's history at all. Nothing
had been pushed, so nothing was disturbed.
