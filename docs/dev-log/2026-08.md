## 2026-08-29 — Capacity ramp: the knee, what queues, and a twenty-second outage

**Commits:** pending — superproject (`docs/`, `tests/load/README.md`). No code
or configuration changed; this session was measurement.

**Context.** The load stage earlier the same day passed every threshold and
saturated nothing — 4 busy Tomcat threads out of 200 at 20 concurrent users.
That answers "is it healthy", not "where does it bend". Asked to raise
concurrency until p95 climbs sharply, errors appear, or something saturates.

**Method.** A capacity ramp rather than the canned `stress` stage: the same
plan repeated with one variable changed. Four steps at 20/50/200/800 threads
holding the load-stage think time, then three at 100/200/500 threads with think
time off — which concentrates the same offered load into far fewer threads and
keeps JMeter off the critical path. Client latency from the `.jtl`, server
latency and saturation counters from Prometheus over the same window, and the
first quarter of every step discarded as warm-up.

**Findings.**

1. **The knee is at ~2 100 req/s on the read path.** Throughput was flat —
   2 203, 2 089, 2 226 req/s — across a 5× rise in concurrency, while p95 grew
   111 → 256 → 447 ms. Below the knee the platform got *faster* as it warmed:
   p95 61 ms at 20 threads, 19 ms at 800.
2. **The queue forms at the HikariCP pool**, left at its default of 10: pinned
   at 10 active with 78, then 180, then 189 threads waiting. Tomcat filled
   behind it, reaching all 200 threads at the last step.
3. **But the pool is not the ceiling.** Raising it to 50 on product-service and
   repeating the same step cut client p95 from 256 to 199 ms and the queue from
   180 to 72 — and left throughput unchanged at ~2 000 req/s, while the
   service's CPU went from 34% to 52%. The pool decides where requests wait,
   not how many finish.
4. **CPU is the actual limit, and it is the host's.** Sampled during the
   200-thread step: product-service ~4.2 cores, MySQL ~2.7, gateway ~2.2 —
   about 9.3 of 12, before counting JMeter. The 2 100 req/s figure is a floor
   for the platform, not a measurement of it.
5. **No errors at any step.** Not one 5xx, no Hikari timeout (waits of
   hundreds of milliseconds against a 30-second timeout), heap under 220 MiB,
   GC under 2%. The failure mode past saturation is unbounded latency, not
   rejection — which is its own hazard: a client with a timeout experiences
   failure while the server records success.
6. **The ordering path bends earlier and elsewhere.** At 200 threads with no
   think time it managed 570 req/s with order-service's Tomcat at 200/200 and
   189 waiting on connections — while product-service answered in **22 ms**
   with 14 threads busy. The documented prediction (order-service saturating
   *on product-service's behalf*, per ADR-0009) is half right: the right
   service saturates, for the wrong reason. It queues on its own database
   connections, not on a slow catalogue.

**The accident worth keeping.** Recreating the `product-service` container
mid-run — to change its pool size — produced **86 421 failures in a 20-second
window, 87% then 92% of all requests**, followed by complete recovery with no
intervention. The gateway went on load-balancing to the dead instance's address
until Eureka evicted it, and with no retry filter and no health-checked
instance selection every one of those hops came back to the caller as a 503.
Recorded as **BUG-23**. A manual click-through would have seen a few errors and
a working refresh; only sustained traffic makes a twenty-second hole visible.

**Changes.**
- `docs/backend/known-defects.md` — BUG-23 added, header note updated.
- `docs/quality/performance-testing.md` — the ramp recorded in §7; §8's
  predictions given verdicts (one confirmed as a queueing point but denied as a
  ceiling, one half right with the wrong mechanism, one contradicted); a new
  §3 subsection documenting the ramp recipe so it is repeatable.
- `docs/quality/test-report.md` — Run D; defect count now 5 found by testing.
- `docs/architecture/system-overview.md` — roadmap reordered: retry and
  health-checked load balancing now lead it, with the measurement attached.
- `tests/load/README.md` — the ramp recipe and where the knee sits.

**Notes.** The pool experiment ran from an override file in the scratchpad, not
from a change to `backend/docker-compose.yml`, and product-service was restored
to the committed configuration afterwards — verified by reading
`hikaricp_connections_max` back from its metrics endpoint. Stock was raised to
200 000 a product beforehand so no step could run the catalogue dry mid-ramp.

## 2026-08-29 — First full-stack load run, and the defect it found

**Commits:** pending — superproject (`tests/load/`, `docs/`, `CHANGELOG.md`).
No submodule code changed; the images were rebuilt from the instrumentation
committed in the entry below.

**Context.** The metrics stack and the JMeter plans went in on 2026-08-27
without ever meeting a running platform — Docker was not up on this machine, so
the plans had only been proved against a Node stub. Asked to run them for real.

**Changes.**
- `tests/load/data/search-keywords.csv` — replaced the invented keywords
  (`laptop`, `gaming`, `rtx`) with terms that exist in the seeded catalogue.
  None of the originals matched a product name, so every search answered 400.
- `tests/load/catalogue-browse.jmx` — new `page.max` property (default 1, which
  suits 14 products at pageSize 12) instead of a hard-coded 0–4 page range; the
  search step now goes through the `?keyword=` filter on the listing endpoint
  rather than `/products/keyword/{keyword}`; the assertion pins 400 as current
  behaviour and names BUG-04.
- `tests/load/order-checkout.jmx` — the payment method is a property, defaulting
  to `online` (what the SPA sends) instead of the hard-coded `cod`.
- `docs/backend/known-defects.md` — **BUG-22** added.
- `docs/quality/performance-testing.md` — §7 filled in with the run; §8 marked
  as unsettled; a new subsection on the two things the harness cannot measure.
- `docs/quality/test-report.md` — Run C added, defect count and report date
  updated.
- `docs/requirements/srs.md`, `tests/load/README.md`, `CHANGELOG.md` — the
  measured result, and what it does and does not verify.

**Findings.** Three, in the order they appeared.

1. **The catalogue smoke stage failed 39% of its samples** — before any load.
   Two causes, both the platform's: a page past the last one answers
   `400 "No Products Exist!!!"` and so does a keyword that matches nothing
   (`BUG-04`), and the seeded catalogue holds 14 products, so pages 2–4 of the
   invented range were all misses.
2. **`GET /products/keyword/{keyword}` cannot be load tested with JMeter at
   all.** It answers a *successful* search with `302 FOUND`, a JSON body, and no
   `Location` header (`BUG-12`). JMeter throws "Missing location header in
   redirect" from its HTTP layer — before `follow_redirects` is consulted, as a
   one-sampler probe confirmed, so no sampler setting can work around it. The
   register said "API tooling mis-handles it"; the stronger statement is that a
   standard tool cannot sample it. Search is now measured through the
   `?keyword=` filter, which is what the SPA's search box uses anyway.
3. **Every order placed with `cod` answered 500** — the new `BUG-22`.
   `Payment.paymentMethod` carries `@Size(min = 4)`, the path variable is never
   validated on the way in, and the violation surfaces as a
   `ConstraintViolationException` at flush time, after product-service has
   already decremented stock. `cod` is exactly what the system and acceptance
   suites send; those cases are destructive-gated and had never been executed,
   so nothing had contradicted their `201` expectation until now.

**The run itself.** Smoke first, then the load stage of both plans, 20 threads
for 5 minutes each: 11 060 samples, **zero errors**, ~19.5 req/s at the
plateau. Catalogue p95 61 ms against the 500 ms budget; place-order p95 102 ms
against 2 s. Server side agreed — gateway p95 67 ms, product-service 36 ms,
order-service 81 ms — and nothing came close to saturating: 4 busy Tomcat
threads of 200, no Hikari connection ever waiting, heap under 135 MiB per JVM.
So the predicted bottlenecks are all still open; they live above 20 concurrent
users, and the stress stage is the run that will settle them.

**Notes.** Stock was raised to 5 000 a product before the ordering run — 306
units would have sold out inside a minute and the run would have measured the
sold-out path instead. Two environment details worth recording: the stale
`mysql`/`config-server`/`discovery-service` containers from the `backend/`
Compose project collided with the root project by name and had to be brought
down first (the mutual-exclusion rule in `docs/operations/docker-setup.md`,
observed in the wild), and the throw-away JMeter install used here is missing
`bin/reportgenerator.properties`, so runs were taken with `--no-report` and the
numbers read from the raw `.jtl`. Grafana was verified end to end — both
dashboards provisioned into the TechZone folder, the datasource resolving, and
a p95 query returning data through Grafana's own proxy.

JMeter's bundled Groovy does not know that class file version. The project
targets Java 21, where it would have worked, but a scriptless element is one
less thing to be surprised by, so the Groovy went.

## 2026-08-26 — Let every role change their own password from /profile

**Commits:** pending — backend (`user-service`), frontend, and the superproject
(`docs/`, `CHANGELOG.md`).

**Context.** No self-service way existed for a customer, seller or admin to
change their own password once signed in; the only password write path was
signup. Asked to add one at `/profile`, with a verify-then-change flow and
visible feedback at every step, that ends in a notification to the user.

**Changes.**
- `backend/user-service/.../security/request/VerifyPasswordRequest.java`,
  `ChangePasswordRequest.java` — new request DTOs (`currentPassword`;
  `currentPassword`/`newPassword`/`confirmPassword` with the same 6–40 length
  rule signup uses).
- `backend/user-service/.../service/AuthService.java`,
  `AuthServiceImpl.java` — `verifyCurrentPassword` (match-only, no write) and
  `changePassword` (re-verifies the current password, rejects a mismatched
  confirmation and a new password identical to the old one, then hashes,
  saves, and notifies).
- `backend/user-service/.../service/NotificationProducer.java` —
  `sendPasswordChangedEmail`, publishing through the same exchange/routing key
  as the existing welcome email.
- `backend/user-service/.../controller/AccountController.java` — new
  controller at `/api/users/password{,/verify}`, deliberately **not** under
  `/api/auth/**`: that prefix is public at the gateway (see
  `api-gateway/src/main/resources/application.yaml`), so a password endpoint
  living there would reach `AuthUtil.loggedInUser()` with no cookie at all and
  fail as an unhandled `500` instead of a clean `401`. `/api/users/**` is not
  on the public-path list, so the gateway itself enforces the JWT cookie
  before the controller runs — confirmed live while testing: an expired
  cookie came back as gateway `401`, not a service-level error.
- `backend/user-service/src/test/.../unit/AuthServiceImplTest.java`,
  `integration/AccountControllerIntegrationTest.java` (new) — unit coverage
  for both service methods (match, mismatch, same-password, and the
  notification call) and HTTP-layer coverage for validation and the
  `APIException` → 400 mapping.
- `frontend/src/store/action/index.js` — `verifyCurrentPassword` and
  `changeUserPassword` thunks, following the existing `setLoader`-callback
  style of `authenticateSigninUser` rather than the global error-reducer
  loading flags.
- `frontend/src/components/profile/ChangePasswordModal.jsx` (new) — the
  two-step dialog: current password + Verify (spinner while in flight, green
  "Verified" badge on success, a "Change" link to redo it), then new password
  + confirm (client-side length/match checks gating the submit button) with a
  toast on success or failure.
- `frontend/src/components/profile/Profile.jsx` — a "Security → Change
  Password" action added to the profile card outside the
  regular-user-only block, so it renders for customer, seller and admin
  alike.
- `docs/backend/api-reference.md`, `docs/backend/services/user-service.md`,
  `docs/backend/services/notification-service.md`,
  `docs/frontend/overview.md` — documented the two new endpoints, the DTOs,
  the public-path reasoning, the new RabbitMQ email variant, and the frontend
  flow.

**Notes.** Verified end to end against the Mode 3 hybrid-dev stack already
running on this machine (backend `.env` carries a real `MAIL_PASSWORD`, so
the queued email is a genuine send, not a stub): signed in as `admin`,
changed the password, confirmed both calls returned `200` and the RabbitMQ
message was published and acknowledged, then reverted the account's password
back to its seeded value in the same session so the demo credentials in
`docs/operations/running-locally.md` keep working for anyone else using this
stack. Along the way, an expired JWT cookie from an earlier session produced
a gateway `401` on the first verify attempt — the exact failure mode the
`/api/users/**` placement was chosen to get right instead of a bare `500`.

## 2026-08-26 — Seed the Mode 3 dev catalogue, fix image 404s, document the whole flow

**Commits:** pending — touches the superproject (`docs/`) and the local,
gitignored `.vscode/launch.json`; no submodule code changed.

**Context.** After setting up Mode 3 hybrid dev (see the entry below), the
shop loaded with zero products, and after seeding, product images all 404ed.

**Findings.**
- The catalogue was empty because the demo seeder (`backend/seed-db/`, the
  `db-seed` Compose service) only ever writes to `ecommerce_product` — the
  schema `prod` uses. `dev` uses a separate,
  per-service schema (`laptop_ecommerce_graduation_project_product_service`),
  which the seeder has no path to and which has no seeding mechanism of its
  own.
- Once seeded, every product image 404ed. Root cause: the superproject's
  `.vscode/launch.json` (built from
  [docs/development/ide-debug-setup.md](../development/ide-debug-setup.md))
  launches each service with no `cwd`, so the Java debugger's working
  directory defaults to the superproject root. `ImagePathUtils.resolveConfiguredPath`
  (`backend/product-service/.../imageutil/ImagePathUtils.java`) only
  recovers when the process starts from `backend/` — one level above
  `product-service/` — not from the superproject root, two levels above. It
  silently resolved the image folder to `<superproject-root>/images/`, which
  does not exist, instead of `backend/product-service/images/`.

**Changes.**
- Seeded the running `dev` schemas once by hand: first via
  `backend/seed-db/run-seed.sh` run directly from the host against the
  container's published port with `PRODUCT_DB`/`USER_DB` overridden; then
  found the cleaner, portable form — `docker compose --profile seed run --rm
  -e PRODUCT_DB=... -e USER_DB=... db-seed` from `backend/` — which reuses
  the existing `db-seed` service over the Compose network and needs no local
  MySQL client. Reused the existing script and `catalogue.sql` unchanged, no
  new SQL file. Result: 14 products across 4 categories, owned by `seller1`,
  `product_seq` raised past the seeded ids.
- `.vscode/launch.json` (gitignored, local machine only) — added
  `"cwd": "${workspaceFolder}/backend"` to all five business-service debug
  configurations.
- `docs/development/ide-debug-setup.md` — updated the canonical
  `launch.json` example with the same `cwd` and an explanation of why it
  matters; added **Step 8 — Seed the catalogue** (the `docker compose
  --profile seed run` command above) and **Step 9 — Verify** (curl checks for
  the product list and one image), so Mode 3 is now a single, complete,
  copy-pasteable walkthrough end to end; extended the troubleshooting table.
- `docs/operations/database-seeding.md` — new section, "Seeding under the
  `dev` profile (Mode 3)", documenting the `PRODUCT_DB`/`USER_DB` override as
  the supported way to seed a hybrid-dev stack; everything else about the
  seeder (idempotency, the `product_seq` bump, the seller lookup) applies
  unchanged.

**Notes.** The seeded rows live only in the `mysql_data` volume — dropping it
(`docker compose down -v` in `backend/`) means running Step 8 again. There is
still no *automatic* seeding path for `dev` (no profile flips it on the way
`prod,seed` does); it is always a deliberate, one-off command.

## 2026-08-26 — Give the seeded catalogue real product photographs

**Commits:** pending — touches `backend/` (seed SQL, Dockerfile, image files),
`frontend/` (one CSS class) and the docs.

**Context.** The demo catalogue seeded every product with `image =
'default.png'`, chosen to mirror what `ProductServiceImpl.addProduct` writes for
a product created through the API. But no file called `default.png` ships
anywhere in the repository, and the product-service `Dockerfile` never copied
`images/` into the runtime stage at all — so a freshly seeded shop rendered
fourteen broken images. The request was simply for the seeder to carry real
pictures.

**Where the images came from.** Wikimedia Commons, via its `api.php` search,
filtered to JPEG and picked by eye — every candidate was downloaded and looked
at before selection, which is how keyboard close-ups, port macros, a video-call
screenshot showing participants' faces, and a scuffed second-hand lid were
rejected. Commons does not hold a photograph of every exact model in the
catalogue; where it does not, the nearest machine of the same make and class
stands in, and `CREDITS.md` names what was actually photographed so no image is
passed off as a model it is not. Files are served through Commons' own
thumbnailer at 900px wide: 1.7MB for all fourteen, versus tens of megabytes for
the originals. PNG sources were dropped in favour of JPEG after two candidates
resolved to multi-megabyte thumbnails.

Licences are CC0, CC BY 2.0/4.0 and CC BY-SA 2.0/4.0. The attribution table
lives in `images/seed/CREDITS.md`, beside the files rather than mirrored into
`docs/`, because CC BY and CC BY-SA require the credit to travel with the work —
a second copy would only drift. `docs/README.md` records that decision in its
Upstream Sources table.

**Changes.**
- `backend/product-service/images/seed/` — new. Fourteen JPEGs, one per seeded
  product, plus `CREDITS.md` giving source, author and licence for each.
- `backend/product-service/Dockerfile` — copies `images/seed` into the runtime
  stage. Only `seed/`, not all of `images/`: the rest of that directory is
  runtime upload scratch and runs to tens of megabytes.
- `backend/seed-db/catalogue.sql` — `image` is now `seed/<slug>.jpg` per row.
  Nothing else about the seed changed.
- `frontend/src/components/shared/ProductCard.jsx` — added `object-cover` to the

*A defect came out of the writing, before anything was even run.*
`JwtUtilsTest` was written expecting
`validateJwtToken(tamperedToken)` to return `false`; it threw instead. All four
validators catch `MalformedJwtException`, `ExpiredJwtException`,
`UnsupportedJwtException` and `IllegalArgumentException` — but not
`SignatureException`, which is exactly what a forged-but-well-formed token
produces. Garbage is caught; a real forgery is not. Filed as **BUG-19**. It is
not an authentication bypass, but at the gateway it turns a `401` into a `500`,
which tells an attacker their token was structurally acceptable. Three
characterisation tests pin it. Not fixed here — the task was to test, and a
one-line security change deserves its own reviewed commit.

*Characterisation over aspiration.* Thirteen register entries now have a test
that asserts the behaviour the platform **actually has** — BUG-04's `400` for an
empty search, BUG-12's `302` for a successful read, SEC-01's self-granted
`ROLE_ADMIN`. Asserting the behaviour we want instead would leave the suite
permanently red, and a permanently red suite is an ignored suite. Each such test
names its defect ID and states, in a comment or an assertion message, what the
expectation becomes once the defect is fixed. Fixing a defect therefore turns
its test red on purpose — which is the review moment a security fix should get.

- `user-service` maps its entity to a table called `user`, which H2 treats as a

  passes for the first time.
- `@WebMvcTest(AuthController.class)` returned `403` on every request: Boot
  applies its default security (CSRF on) and does not pick up a `SecurityFilterChain`
  from a plain `@Configuration`. Resolved with `@Import(SecurityConfig.class)`,
  which is the better test anyway — the filter chain under test is now the one
  the service deploys with.

*Why no Vitest.* The front-end reducers and helpers import nothing, so Node can
load them as plain ES modules and unit-test them with no npm install and no
change to `frontend/package.json`. Component rendering does need Vitest, jsdom
and Testing Library; that is listed as a known gap rather than half-done.

*Verification.* **213 backend tests, 44 front-end tests, 54 system tests and 31
acceptance tests — 342 in total, all green** — the last two suites against the
Compose stack (`COMPOSE_PROFILES=prod,seed`). The remaining 8 written tests
place real orders and sit behind `RUN_DESTRUCTIVE=1`; they were not run.

*The live run paid for itself immediately.* Three things came out of it:

1. **A stale deployment.** `access-control.test.js` failed: a plain customer
   reached `/product-manager/api/seller/products`. The repository maps that path
   to `ROLE_SELLER`, but the running gateway image had been built on 2026-08-22,
   three days before commit `c4065e5` added the mapping. The test was right and
   the container was old. Rebuilding api-gateway and product-service — the only
   two modules with source changes since — turned it green. This is the failure
   only a system test can produce: the unit test proves the filter enforces the
   policy, the integration test proves the file declares it, and only the system
   test asks whether the thing actually running does it.

2. **BUG-20.** `GET /order-manager/api/carts/users/cart` answers **500** for a
   customer who has never had a cart: `CartServiceImpl.getCart` calls
   `findCartByEmail(...).getCartId()` with no null check, and the cart row is
   only created by the first add. Every newly registered customer hits it the
   first time they click the cart icon. No unit test would have caught it — it
   needs a real account that has genuinely never had a cart.

3. **BUG-21, by accident, which is the interesting part.** `node --test` runs
   each file in its own process. Two suites signed in as the same seeded
   customer and added the same product at the same instant; both saw no existing
   line and both inserted one. With no unique constraint on
   `cart_item (cart_id, product_id)`, both rows survived — and because
   `findCartItemByProductIdAndCartId` returns a single entity, **every**
   subsequent cart request for that account answered
   `IncorrectResultSizeDataAccessException: 2 results were returned`.
   Permanently. The account's cart had to be repaired with SQL before the suite
   could run again. High severity, reachable by double-clicking "Add to cart",
   and entirely invisible to any single-threaded test.

   The suites now run with `--test-concurrency=1` so they stop stumbling into it
   on every run. That is a deliberate trade, recorded in the strategy document:
   the suite no longer tests for BUG-21, and BUG-21 has no regression test.

*Cleanup performed.* The duplicated `cart_item` rows this created for `user1`
were deleted and that cart's total reset to 0, restoring the state the suite's
own teardown intends. No other data was touched; the throw-away accounts the
registration scenarios create were left in place.
