## 2026-08-24 — Stripe Payment Element rendered empty on the checkout page

**Commits:** none — no source change was needed.

**Context.** The final checkout step showed the "Payment Information" heading
and the Pay button, but no card fields. Stripe.js reported
`invalid_request_error — Invalid API Key provided: pk_test_***here`, and the
masked suffix matched the placeholder shipped in `.env.example`.

**Changes.**
- No file changed. The root `.env` already held a valid publishable key, and
  [`frontend/src/components/checkout/StripePayment.jsx`](../../frontend/src/components/checkout/StripePayment.jsx)
  already read it correctly through `import.meta.env`.

**Notes.** The root cause was the frontend **image**, not the environment file.
Vite inlines every `VITE_*` variable into the bundle at build time
([`frontend/Dockerfile`](../../frontend/Dockerfile) writes them into
`.env.production` before `npm run build`), so the `techzone-frontend` image
still carried the placeholder from the build that happened while `.env` was
un-filled. Restarting the container could never fix it — nginx serves a static
bundle. `docker compose build frontend` followed by `docker compose up -d
frontend` produced a bundle carrying the real key.

The first diagnosis was wrong in an instructive way: it assumed a Vite dev
server and recommended editing `.env` plus `npm run dev`. This stack runs the
frontend from a built image, where the equivalent step is a rebuild. The
build-time/runtime split is now called out in
[`../operations/docker-setup.md`](../operations/docker-setup.md) — `VITE_*`
variables need a rebuild, `API_GATEWAY_URL` only needs a restart.

Verifying which key a running container actually serves:

```sh
docker exec frontend sh -c 'grep -ro "pk_test_[A-Za-z0-9_]*" /usr/share/nginx/html/assets'
```

## 2026-08-24 — Run backend and frontend from one Compose stack

**Commits:** `adf69ce` (superproject), `3b25e16` (backend)

**Context.** The backend had its own `docker-compose.yml` and the frontend had
none, so a full-stack run meant starting two things by hand and reconciling
their networks.

**Changes.**
- `docker-compose.yml` (root) — pulls in `backend/docker-compose.yml` via
  `include` so the backend services keep a single definition, and adds the
  `frontend` service on the same `ecommerce-network`.
- `frontend/Dockerfile` — two-stage build: Vite bundle, then nginx serving the
  static output with a templated reverse proxy to the gateway.
- `backend/docker-compose.yml` — health checks corrected so dependent services
  wait for genuinely ready dependencies rather than merely started containers.

**Notes.** `VITE_BACK_END_URL` is deliberately empty in the stack: the SPA then
calls its own origin and nginx proxies `/user-manager`, `/product-manager`, and
`/order-manager` into the Docker network. No CORS preflight, and the auth cookie
stays first-party.

Local MySQL already holds port 3306 on the development machine, so the stack
publishes the container on `MYSQL_PORT=3307`.

## 2026-08-24 — Per-service backend docs and a defect register

**Commits:** `5cb8e83` (superproject)

**Context.** `backend/README.md` covered the system at a high level, but each
service's internals — routes, config keys, messaging topology — lived only in
the source.

**Changes.**
- `docs/backend/services/*.md` — one document per service: gateway, config
  server, discovery, user, product, order, notification.
- `docs/backend/known-defects.md` — a register of defects found during a source
  audit, each with severity, reproduction, and proposed fix.

**Notes.** `known-defects.md` names unpatched weaknesses, including the absent
token revocation path and the JWT lifetime. Keeping that register public was a
deliberate call: the platform runs locally only, so the file is an honest
engineering artefact rather than an attack map, and being able to enumerate your
own system's weaknesses is worth more in a defence than pretending it has none.
Revisit before the platform is ever deployed to a reachable host — at that point
the exploitable detail would need to move out of the repository.
