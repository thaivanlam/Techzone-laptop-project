## 2026-10-12 — Resource overlays: a small stack for development, a bounded one for load runs

**Commits:** `e8a2ad7` (backend), and the superproject commit that records it —
both on a `resource-overlays` branch.

**Context.** The request was to reduce what the containers cost on the
development laptop. Measuring first showed memory, not CPU, was the problem:
about 3.6 GiB at idle, two thirds of it in the seven Spring Boot services,
because no container had a limit and no Dockerfile passed a JVM flag — each JVM
sized itself from the whole 7.6 GiB Docker VM. The brief asked for separate
development and benchmark configurations, validated rather than assumed.

**Changes.**

- `backend/docker-compose.dev.yml` (new) — overlay for the seven JVM
  containers: SerialGC, 45% heap, 512k stacks, a 64 MiB code cache, C1-only
  compilation; ceilings of 320–576 MiB and one core each.
- `backend/docker-compose.benchmark.yml` (new) — overlay for load runs: full
  JIT, 50% heap, G1 pinned; ceilings of 384–1 024 MiB and 1–6 cores.
- `docs/operations/resource-limits.md` (new) — both overlays, the reason for
  each flag and limit, validation and measurement commands, the before-and-after
  procedure, and the optional WSL2 cap.
- `docs/operations/resource-limits-measurements.md` (new) — what was measured,
  and the conditions each figure was taken in.
- `docs/operations/docker-setup.md`, `running-locally.md`,
  `configuration-reference.md`, `troubleshooting-runbook.md` — how to start each
  mode, what the overlays set, and the exit-137 symptom.
- `docs/quality/performance-testing.md`, `tests/load/README.md`,
  `tests/README.md` — which overlay a load run uses, the comparison run, and the
  longer request timeout the live suites need under the development overlay.
- `docs/README.md`, `CLAUDE.md`, `AGENTS.md`, `CHANGELOG.md` — index rows and
  the release note.

**Notes.**

- The base Compose files were not touched. Running without an overlay gives
  exactly the previous stack, which is what made a before-and-after possible.
- **G1 had to be pinned in the benchmark overlay.** Below 1 792 MB of container
  memory the JVM stops treating itself as server-class and falls back to
  SerialGC, so any limit in this range would have changed the collector under
  the measurement. Checked on the image with `-XX:+PrintFlagsFinal`.
- Measured, one run each: the development overlay took the seven JVMs from
  2 365 MiB to 1 462–1 606 MiB. The benchmark overlay left the catalogue load
  stage where it was — 19.4 against 19.6 req/s, no errors, p95 within noise.
- `TieredStopAtLevel=1` was kept after measuring both sides of it: about
  350 MiB saved, for a 2.4x slowdown on the seller order list. That slowdown
  pushes one system test past its 15-second timeout on a database still holding
  15 511 orders from the August load runs; it passes at 30 seconds.
- An expectation that was wrong: one core per service was predicted to slow
  startup. It was faster — 6–18 s per service against 8–32 s under the benchmark
  overlay — because C1-only compilation does much less work at boot.
- Keycloak, MySQL and RabbitMQ were measured and left alone; the candidates and
  why each was not applied are in the new document. Nothing was changed on the
  Windows host.
- Not run: any checkout or payment, the `order-checkout` plan, the stress stage,
  and the three suites that create realm accounts. JMeter 5.6.3 was downloaded
  to a temporary directory for the comparison and is not part of the repository.
- Found along the way and left as found: `gateway-routing.test.js` expects 404
  for an unknown prefix and gets 401; the gateway's `/actuator/prometheus`
  answers 401 without a token, which `observability.md` does not say and which
  would matter to the Prometheus scrape — not checked, the profile was off;
  and the `rabbitmq` container shows CPU spikes of 160–320% while idle, probably
  its healthcheck.
- No ADR. The overlays are opt-in and change no default; if one of them becomes
  the default way to run the stack, that is the decision to record.

## 2026-10-12 — Fix BUG-01: a failed checkout no longer keeps stock

**Commits:** `7909842` (backend), and the superproject commit that records it.

**Context.** The request was to fix `BUG-01` from the defect register: an order
that failed on a later line left the earlier lines' stock decremented in
product-service, because `placeOrder` called `reduce-stock` once per line inside
a local transaction that could not roll the remote writes back.

**Changes.**

- product-service `ProductRepository` — `reduceStock`, a conditional
  `UPDATE ... WHERE quantity >= :q`, and `restoreStock`, its inverse.
- product-service `ProductServiceImpl`, `ProductController`, new
  `InventoryBatchRequest` / `InventoryLine` — `POST /api/internal/products/reduce-stock`
  takes every line of an order in one `@Transactional` call, all or none;
  `POST /api/internal/products/restore-stock` gives lines back.
- order-service `ProductServiceClient`, `RestTemplateProductServiceClient`, new
  `StockLine` — `reduceProductQuantity` replaced by `reduceProductQuantities`
  and `restoreProductQuantities`.
- order-service `OrderServiceImpl.placeOrder` — reserves the whole cart before
  writing anything; everything after it runs in a `try` whose `catch` restores
  the stock and rethrows; an explicit flush brings constraint failures inside
  that `try`.
- Tests — the `BUG-01` characterisation test in `OrderServiceImplTest` inverted,
  four cases added for the compensation path; batch and restore cases in
  `ProductServiceImplTest`, `ProductControllerIntegrationTest`,
  `ProductRepositoryIntegrationTest` and `ProductServiceClientIntegrationTest`.
- `docs/` — the register entry and every document that described the per-line
  loop; `CHANGELOG.md`.

**Notes.**

- The register offered a batch call *or* compensation. Both were needed: the
  batch call makes the reservation atomic, but the order can still fail after
  it (a persist error, the RabbitMQ publish), and only compensation covers that.
  Doing both also closed the lost-inventory half of `BUG-11` and `BUG-22`.
- The batch call uses an atomic `UPDATE` rather than repeating the single-line
  endpoint's read-modify-write, so checkout no longer reaches `BUG-02` or
  `BUG-09`. Both stay open: the single-line endpoint still exists, now unused,
  with its own characterisation tests.
- Not covered, and written into the register as such: order-service dying
  between the reservation and the commit, a lost reservation response, a commit
  failure after the flush, and a restore call that fails (logged at ERROR with
  the lines). These need an outbox or an expiring reservation.
- Verified by the unit and integration suites of both services (order-service
  70 tests, product-service 84, all passing). **Not** run against a live stack;
  no system test in `tests/` drives a failing multi-line checkout yet.
- No ADR was written. Reservation plus compensation is arguably a platform-level
  choice; if it is to be recorded as one, it wants an ADR of its own.
- `backend/README.md` still describes the per-line call; it is the submodule's
  own file and was left alone.
