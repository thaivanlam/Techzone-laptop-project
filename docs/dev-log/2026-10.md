## 2026-10-12 — Fix BUG-01: a failed checkout no longer keeps stock

**Commits:** `7909842` (backend), and the superproject commit that records it.

**Context.** The request was to fix `BUG-01` from the defect register: an order
that failed on a later line left the earlier lines' stock decremented in
product-service, because `placeOrder` called `reduce-stock` once per line inside
a local transaction that could not roll the remote writes back.

**Changes.**

- product-service `ProductRepository` — `reduceStock`, a conditional
  `UPDATE ... WHERE quantity >= :q`, and `restoreStock`, its inverse.
- product-service `ProductServiceImpl`, `ProductController`, new
  `InventoryBatchRequest` / `InventoryLine` — `POST /api/internal/products/reduce-stock`
  takes every line of an order in one `@Transactional` call, all or none;
  `POST /api/internal/products/restore-stock` gives lines back.
- order-service `ProductServiceClient`, `RestTemplateProductServiceClient`, new
  `StockLine` — `reduceProductQuantity` replaced by `reduceProductQuantities`
  and `restoreProductQuantities`.
- order-service `OrderServiceImpl.placeOrder` — reserves the whole cart before
  writing anything; everything after it runs in a `try` whose `catch` restores
  the stock and rethrows; an explicit flush brings constraint failures inside
  that `try`.
- Tests — the `BUG-01` characterisation test in `OrderServiceImplTest` inverted,
  four cases added for the compensation path; batch and restore cases in
  `ProductServiceImplTest`, `ProductControllerIntegrationTest`,
  `ProductRepositoryIntegrationTest` and `ProductServiceClientIntegrationTest`.
- `docs/` — the register entry and every document that described the per-line
  loop; `CHANGELOG.md`.

**Notes.**

- The register offered a batch call *or* compensation. Both were needed: the
  batch call makes the reservation atomic, but the order can still fail after
  it (a persist error, the RabbitMQ publish), and only compensation covers that.
  Doing both also closed the lost-inventory half of `BUG-11` and `BUG-22`.
- The batch call uses an atomic `UPDATE` rather than repeating the single-line
  endpoint's read-modify-write, so checkout no longer reaches `BUG-02` or
  `BUG-09`. Both stay open: the single-line endpoint still exists, now unused,
  with its own characterisation tests.
- Not covered, and written into the register as such: order-service dying
  between the reservation and the commit, a lost reservation response, a commit
  failure after the flush, and a restore call that fails (logged at ERROR with
  the lines). These need an outbox or an expiring reservation.
- Verified by the unit and integration suites of both services (order-service
  70 tests, product-service 84, all passing). **Not** run against a live stack;
  no system test in `tests/` drives a failing multi-line checkout yet.
- No ADR was written. Reservation plus compensation is arguably a platform-level
  choice; if it is to be recorded as one, it wants an ADR of its own.
- `backend/README.md` still describes the per-line call; it is the submodule's
  own file and was left alone.
